## 一句话定位

`SceneBlueprint` 更适合被定义为一套面向 Unity 的场景级蓝图制作、导出与运行框架，而不只是一个节点编辑器。

它的核心价值不在于“能画节点图”，而在于：

- 用 DSL 和代码生成体系统一蓝图定义来源。
- 用 Session 化编辑器工作台承接蓝图制作、分析、预览和导出。
- 用 Marker、Annotation、Spatial 抽象把蓝图逻辑稳定绑定到真实场景。
- 用稳定契约把编辑器结果导出为运行时可消费的数据。
- 用解释器式运行时、状态域、快照和测试工具承接执行、观察和调试。

## 项目目标与解决的问题

从当前代码看，`SceneBlueprint` 解决的不是“策划能不能连节点”这种单点问题，而是一组典型的场景流程系统问题。

### 1. 蓝图定义容易分散和失控的问题

当行动类型、端口、Marker、Signal、Tag 维度越来越多时，如果仍然依赖手写注册和口口相传，系统会很快出现：

- 定义来源分散
- 编辑器和运行时认知不一致
- 新能力接入成本高
- 类型约束难以统一

`SceneBlueprint` 通过：

- `.sbdef`
- `SbdefAssetImporter`
- `SbdefPipeline`
- 各类 `Emitter`
- `ActionRegistry`

把定义来源尽量收敛到正式 DSL 和生成链路上，再把生成结果接入编辑器与运行时。

### 2. 编辑器逻辑、图状态和窗口生命周期耦合的问题

很多工具型项目一旦功能变多，就容易出现：

- 大窗口脚本不断膨胀
- 状态散落在多个 UI 组件里
- 重载、切场景、恢复流程变得脆弱
- 新功能接入需要反复修改主窗口

`SceneBlueprint` 通过：

- `SceneBlueprintWindow`
- `BlueprintEditorSession`
- `BlueprintAnalysisController`
- `BlueprintExportService`
- `NodePreviewScheduler`
- `SubGraphController`

把窗口、会话状态和各类服务分开治理，使编辑器更接近平台化工作台，而不是单体脚本工具。

### 3. 蓝图逻辑难以稳定绑定真实场景的问题

如果蓝图只停留在纯逻辑图层，就会遇到：

- 节点和场景对象之间缺少稳定引用
- 2D / 3D 空间模式难以统一
- 标记系统容易散乱
- 场景对象丢失后难以恢复

`SceneBlueprint` 通过：

- `SceneMarker`
- `MarkerDefinitionRegistry`
- `AnnotationDefinitionRegistry`
- `SpatialModeRegistry`
- `SceneBindingCollector`
- `SceneBindingRestorer`
- `BindingSnapshot`

把逻辑和场景之间的关系做成了可定义、可绑定、可导出、可恢复的一整套机制。

### 4. 编辑结果难以稳定进入运行时的问题

如果编辑器输出不是稳定契约，而是直接耦合运行时对象，就会出现：

- 导出格式脆弱
- 业务层难以接管
- 运行时难以脱离编辑器独立加载
- 编辑器工程和运行时工程难以分离

`SceneBlueprint` 通过：

- `SceneBlueprintData`
- `BlueprintExporter`
- `BlueprintSerializer`
- `BlueprintLoader`

把蓝图编辑结果统一收口到纯数据契约上，降低了编辑器和运行时之间的耦合度。

### 5. 蓝图运行后难以调试和回放的问题

蓝图系统真正困难的地方并不只是“能运行”，而是：

- 运行时状态如何观察
- 节点状态如何定位
- 事件链路如何回放
- 出问题时如何解释

`SceneBlueprint` 通过：

- `BlueprintRunner`
- `TransitionSystem / FlowSystem / SignalSystem`
- `RuntimeStateHost`
- `RuntimeSnapshotService`
- `BlueprintTestWindow`
- `RuntimeSnapshotBrowser`

把解释执行、状态域、快照导出与回放、测试窗口逐步组织成一条更完整的调试链路。

### 6. 工具知识和上下文难以沉淀的问题

随着系统越来越复杂，仅靠口头传递很难支撑后续协作，会出现：

- 新人理解成本高
- 节点说明和源码分离
- AI / 搜索类辅助工具拿不到实时上下文

`SceneBlueprint` 在此基础上又补了：

- `KnowledgeRegistry`
- `PromptAssembler`
- `KnowledgeService`
- 编辑器内 Chat / MCP 接口

让文档、定义、当前蓝图上下文和知识辅助之间开始形成统一入口。

### 7. 编辑过程抗中断和恢复能力不足的问题

工具型项目在真实使用中，经常还会遇到一类不太显眼但很重要的问题：

- 编辑器重载或关闭后临时修改丢失
- 未正式保存的新蓝图难以恢复
- 图结构和场景绑定混在同一资产里，恢复粒度不清晰

`SceneBlueprint` 在这方面补了：

- `BlueprintAsset`
- `BlueprintAssetStore`
- `.blueprint.json` 独立图数据
- `SceneSnapshots`
- `BlueprintAutosaveDraftStore`
- 匿名草稿恢复

这说明它不只是关注“能不能编辑”，还关注“编辑过程是否稳定、是否抗中断、是否便于恢复”。

### 8. 框架默认能力和业务接线容易混在一起的问题

如果框架默认 System、业务侧 System、项目级 baseline 初始化都直接混写在一起，后续就会出现：

- 框架边界不清晰
- 项目迁移成本高
- 测试环境和正式运行环境难以统一

`SceneBlueprint` 通过：

- `BlueprintSystemRegistry`
- `IBlueprintSystemProvider`
- `IBlueprintRunnerConfigurator`
- `BlueprintRunnerConfiguratorRegistry`
- `FrameworkDefault / ProjectBaseline`

把框架内置能力和项目接线能力显式区分开来，更接近可被业务承接的平台型框架。

## 项目架构分层

从当前代码结构来看，`SceneBlueprint` 大致可以拆成以下几层：

### 1. 定义与生成层

这一层负责回答“蓝图系统里到底有哪些正式能力，以及这些能力如何被声明”。

核心职责：

- 定义 Action、Marker、Annotation、Signal、TagDimension
- 通过 DSL 统一能力来源
- 生成编辑器和运行时可消费的代码

核心意义：

- 让定义不再散落在手写注册代码里。
- 让扩展能力接入更接近声明式，而不是补丁式。

### 2. 编辑会话与工作台层

这一层负责回答“用户如何进入一个稳定的蓝图编辑工作台”。

核心职责：

- 管理图状态和窗口生命周期
- 管理 Inspector、分析、预览、导出、子图等服务
- 承担工作区切换、状态恢复和会话隔离
- 管理本地草稿自动保存和匿名草稿恢复

核心意义：

- 让编辑器从单体脚本演进为会话化平台。
- 让新能力接入不必持续污染主窗口。

### 3. 场景语义与空间绑定层

这一层负责回答“蓝图如何接入真实场景和空间语义”。

核心职责：

- 定义 Marker 与 Annotation 类型
- 管理 SceneView 创建、拾取、渲染和交互
- 管理 2D / 3D 空间模式
- 管理场景绑定的收集、校验、恢复和快照

核心意义：

- 让蓝图不只是逻辑图，而是场景语义图。
- 让节点与真实场景之间的关系更稳定、更可恢复。

### 4. 导出与契约层

这一层负责回答“编辑结果如何被稳定传递到运行时”。

核心职责：

- 展平图和子图结构
- 导出节点、连线、变量、场景绑定和元数据
- 组装统一的传输契约
- 支持业务侧导出 enrich 扩展
- 为业务侧编译和派生数据注入预留统一上下文

核心意义：

- 把编辑器内部结构和运行时消费模型隔离开。
- 为工程分层和项目分离提供稳定边界。

### 5. 运行时解释执行层

这一层负责回答“导出的蓝图在运行时如何被加载和驱动”。

核心职责：

- 将契约数据加载为 `BlueprintFrame`
- 维护索引、黑板、边关系和节点状态
- 用 `Runner + Systems` 驱动执行
- 承接控制流、信号、黑板、组合条件等基础语义
- 区分框架默认运行时能力和项目基线接线能力

核心意义：

- 让运行时不依赖编辑器对象。
- 让节点执行更接近解释器式架构，而不是散乱脚本调用。

### 6. 状态观测与调试支持层

这一层负责回答“蓝图运行之后如何被观察、验证和回放”。

核心职责：

- 管理运行时状态域和生命周期
- 导出与回放状态快照
- 提供测试窗口和状态浏览界面
- 承接运行期上下文和知识辅助能力

核心意义：

- 让蓝图系统具备更强的调试性和解释性。
- 让后续复杂能力不至于沦为黑盒运行。

### 7. 持久化与恢复层

这一层负责回答“蓝图编辑过程中的事实源如何被分开保存，以及中断后如何恢复”。

核心职责：

- 将图结构独立存储为 `.blueprint.json`
- 将场景绑定快照独立存储为 `SceneSnapshots`
- 维护本地草稿自动保存
- 支持匿名草稿和正式资产草稿恢复

核心意义：

- 让图结构、场景语义和临时编辑状态各自拥有清晰边界。
- 让工具在重载、关闭和异常中断后更容易恢复现场。

## 最有代表性的亮点

如果要从整个项目里提炼最值得讲的亮点，我认为主要有以下几项。

### 1. 用 DSL 和代码生成统一能力定义来源

这不是简单的“加了一个配置文件格式”，而是把蓝图能力的定义正式提升到语言层和生成层。

价值在于：

- 定义来源更统一
- 编辑器和运行时更容易保持一致
- 扩展新能力时有更清晰的接入路径

这会比“手写了一堆节点定义类”更能体现系统设计能力。

### 2. 编辑器采用 Session + Services 的平台化结构

`SceneBlueprintWindow` 本身是薄壳，真正的状态和服务收拢在 `BlueprintEditorSession` 中，再通过各类 `WindowServices` 协作。

价值在于：

- 降低主窗口复杂度
- 提升可维护性
- 为后续扩展分析、预览、导出、子图、知识面板留下更稳的挂接点

这比常见的“一个 EditorWindow 管所有逻辑”的方式要成熟很多。

### 3. 场景绑定不是附属功能，而是正式的系统层

`SceneBlueprint` 的一个重要区别在于，它不是纯逻辑节点图，而是把 Marker、Annotation、SceneBinding、SpatialMode 做成了正式体系。

价值在于：

- 节点和真实场景可以建立稳定语义关系
- 2D / 3D 模式具备统一抽象
- 场景对象丢失后仍可通过快照与恢复链路回补

这会显著提高项目在“场景工具框架”方向上的辨识度。

### 4. 导出链路重视稳定契约而不是对象直连

编辑器内部图状态最终统一收敛为 `SceneBlueprintData`，这是一条非常关键的工程判断。

价值在于：

- 运行时可以脱离编辑器独立存在
- 编辑器项目和运行时项目具备拆分可能
- 后续业务层可以围绕契约做更清晰的承接

这一点很适合写进简历，因为它体现的是系统边界设计能力。

### 5. 运行时不是脚本集合，而是解释器式执行框架

`BlueprintLoader + BlueprintRunner + Systems + RuntimeStateHost` 这一套组合说明项目并不是简单地“导出后反射执行”，而是在向正式解释执行框架靠拢。

价值在于：

- 节点执行流程更清晰
- 系统扩展更可控
- 状态观察、回放和调试更容易接入

这会让项目从普通工具提升到框架级项目。

### 6. 调试、快照与知识服务已经开始形成辅助闭环

这一部分虽然不是主叙事，但很加分。

价值在于：

- 系统更可观察
- 问题定位手段更丰富
- 文档和工具上下文开始被纳入同一工作流

后续对外写法上可以作为“工程成熟度”的补充说明，而不是主卖点。

### 7. 业务扩展口设计得比较正式

`SceneBlueprint` 不只是框架内部自洽，它还给业务侧预留了比较清晰的接入点。

例如：

- `IExportEnricher`
- `ActionCompilationContext`
- `IBlueprintSystemProvider`
- `IBlueprintRunnerConfigurator`

这些扩展口说明项目不是只打算在单一项目里自用，而是在朝“可被承接、可被定制”的平台方向设计。

### 8. 工具具备较强的抗中断与恢复意识

独立图数据、场景快照、本地草稿自动保存、匿名草稿恢复这些设计，看起来不是最显眼的卖点，但很能体现项目成熟度。

价值在于：

- 编辑过程更稳
- 实验性蓝图不容易丢
- 工具更适合长期使用，而不是一次性演示

## 对项目边界的正确表述

为了让后续简历和作品集表述更稳，下面这些边界需要明确。

### 1. 这是一个完整项目，但不是所有分层都同等成熟

主链路已经很清楚：

- 定义
- 编辑
- 绑定
- 导出
- 执行
- 调试

但 `Application/`、`Domain/` 中仍有部分预留骨架，因此不宜把全部分层表述成“都已经完整业务化落地”。

### 2. 不宜把内部模块写成多个独立项目

`SceneBlueprint` 的价值本来就在于它把多个子系统串成一个闭环。

如果拆成：

- DSL 工具项目
- 场景绑定项目
- 运行时解释器项目

反而会弱化“端到端框架”这一最核心的价值。

### 3. AI / 知识能力适合写成辅助扩展，不适合抢主叙事

这部分很加分，但不宜把项目主定位写成“AI 蓝图工具”。

更稳妥的说法是：

- 在主链路之外，补充了知识检索和上下文辅助能力

而不是：

- 这是一个以 AI 为核心的蓝图系统

### 4. 本地草稿自动保存适合写成工程成熟度，不适合写成主功能

这部分确实很加分，但它更适合服务于“工具健壮性”和“可恢复性”的表述。

更稳妥的说法是：

- 增加了本地草稿自动保存、匿名草稿恢复和场景快照恢复能力

而不是：

- 这是一个以自动保存为亮点的蓝图工具

### 5. 不宜只写成节点编辑器

如果只写“做了一个节点编辑器”，会丢掉以下价值：

- DSL 统一定义
- 场景语义绑定
- 稳定导出契约
- 运行时解释执行
- 状态快照与调试

这会把整个项目压扁。

这几项比单纯强调“做了很多功能”更能体现项目的分量。

## 简历写法建议

如果后续要把这个项目放进简历或作品页，建议遵循以下原则。

### 1. 先讲整体定位，再讲重点闭环

推荐顺序是：

- 先说明这是一个面向 Unity 的场景级蓝图框架
- 再讲它统一了定义、编辑、场景绑定、导出和执行
- 最后补几个最有代表性的模块亮点

不要一上来就按文件夹罗列实现点。

### 2. 强调“统一”和“收口”

这个项目里最有价值的词，不是“做了很多”，而是：

- 统一定义来源
- 统一编辑工作台
- 统一场景绑定
- 统一导出契约
- 统一运行时执行和调试
- 统一业务扩展入口

这会比碎片化功能描述更有说服力。

### 3. 把知识服务放在补充层

可以写，但建议放在后半段，例如：

- 在主链路之外，补充了知识检索和上下文辅助能力，提升工具解释性和协作效率

不要让它喧宾夺主。

下面这部分可以作为后续简历网站项目详情页的基础文案，再按页面结构继续压缩或拆层。

### 项目介绍

`SceneBlueprint` 是一套面向 Unity 的场景级蓝图制作与运行框架，用于统一承接蓝图定义、可视化编辑、场景语义绑定、导出契约和运行时解释执行。

这套系统并不是单纯的节点编辑器，而是试图把“如何声明一种场景行为”“如何在编辑器中制作它”“如何把它稳定绑定到场景对象”“如何导出并在运行时执行它”组织成一条完整闭环。

### 整体设计

- 通过 `.sbdef` 和代码生成链路统一 Action、Marker、Annotation、Signal 等定义来源，降低手写注册和多端不一致的问题。
- 通过 `Window + Session + Services` 的编辑器结构承接图编辑、分析、预览、导出、子图和工作台状态管理，避免主窗口持续膨胀。
- 通过 Marker、Annotation、Spatial 模式和场景绑定机制，把蓝图逻辑稳定接入真实场景，而不是停留在纯逻辑图层。
- 通过 `SceneBlueprintData` 契约、`BlueprintLoader`、`BlueprintRunner` 与多类运行时 System，把编辑结果落到可独立加载和解释执行的运行时链路。
- 通过独立图数据、场景快照和本地草稿自动保存机制，提升编辑过程的抗中断能力和恢复稳定性。
- 通过导出后处理、业务编译上下文、System Provider 和 Runner Configurator，把框架能力与项目接线能力清晰分层。
- 通过状态域、快照导出与回放、测试窗口和知识服务，补充系统的调试性、可观察性和解释能力。

### 重点模块

#### 1. DSL 与定义生成体系

- 设计 `.sbdef` 定义链路，并通过 Importer 与 CLI 生成代码，把 Action、端口、Marker、Annotation、Signal 等能力接入统一注册体系。
- 将定义问题从散落的手写脚本，收敛为更正式的声明式入口，为后续扩展和一致性治理打基础。

#### 2. 编辑器会话与工作台体系

- 将蓝图编辑器拆分为窗口薄壳、会话状态和服务层，统一承接分析、预览、导出、子图和 Inspector 等能力。
- 让编辑器从单体工具脚本演进为可扩展的工作台平台，降低后续功能增长带来的结构膨胀。

#### 3. 场景语义绑定与恢复体系

- 设计 Marker、Annotation、空间模式和场景绑定链路，使蓝图节点能够稳定绑定真实场景对象和空间语义。
- 增加绑定收集、绑定恢复和场景快照恢复能力，提升场景对象变动、丢失或重载后的恢复稳定性。

#### 4. 导出与运行时解释执行体系

- 将编辑器图结构统一导出为稳定的 `SceneBlueprintData` 契约，隔离编辑器内部实现与运行时消费模型。
- 设计 `Loader + Runner + Systems` 的解释执行结构，承接控制流、信号、黑板和组合条件等蓝图基础语义。

#### 5. 持久化恢复与编辑稳定性

- 将图结构独立存储为 `.blueprint.json`，同时把场景绑定快照单独保存，避免不同层次的信息混在同一份资产里。
- 增加本地草稿自动保存和匿名草稿恢复能力，使正式资产与临时编辑状态都具备更稳的恢复链路。

#### 6. 状态调试与知识辅助能力

- 补充运行时状态域、快照导出与回放、测试窗口等能力，提升蓝图运行过程的可观察性和调试效率。
- 在主链路之外接入知识检索和上下文辅助能力，为后续复杂系统的维护和协作提供支持。

#### 7. 业务扩展与项目接线能力

- 在基础导出完成后，系统会继续执行统一的后处理与动作编译，把节点配置整理成更稳定的运行期计划、调试摘要和补充元数据，而不是让运行时、测试工具再各自重复解释原始参数。
- 框架默认能力和项目侧接线被显式拆开：框架负责控制流、信号、黑板、状态域和快照基础设施，项目侧再通过正式扩展入口补充业务 System、服务注册和项目级 bootstrap。

#### 8. 状态快照与回放能力

- 运行时状态不仅支持导出快照，还支持按载荷类型、恢复模式、依赖关系和优先级执行回放，说明这套系统在设计时已经考虑到复杂状态恢复，而不是只做单向日志记录。
- 这让蓝图运行结果不再是一次性的黑盒过程，而是可以被捕获、浏览、重建和定位的可观察状态链路。

### 可补充到项目详情页的正式文案

如果后续你想把当前还偏抽象的几条，直接补到项目详情页里，下面这几段可以直接复用。

#### 业务扩展口

我没有把导出流程停留在“把节点图序列化成 JSON”这一步，而是在导出完成后继续补了一层统一的动作编译与后处理机制。  
这层机制会把流程节点、黑板节点等配置进一步整理成更稳定的运行期计划、调试摘要和传输元数据，使运行时、测试窗口和调试工具不必再各自重复解释原始节点参数。

这套设计的价值在于，业务侧后续增加新节点或新编译逻辑时，不需要直接改动整个导出主流程，而是可以通过统一扩展入口接入，把“框架主链路”和“业务派生能力”更清晰地分开。

#### 项目基线接线

我在运行时层面明确区分了“框架默认能力”和“项目基线能力”。  
框架默认部分负责控制流、信号、黑板、状态域、快照等通用能力；项目侧则通过正式的 System Provider 和 Runner Configurator 入口补充业务 System、服务注册和项目级 bootstrap。

这样做的意义在于，框架本身可以保持稳定边界，而不同项目又能在不污染框架主干的前提下接入自己的运行逻辑、依赖和初始化流程。这让 `SceneBlueprint` 更接近一套可被业务承接的平台型框架，而不是只能在单一项目里自用的工具集合。

#### 状态快照与回放

为了提升蓝图系统的可调试性，我没有把运行过程只当作一次性的状态流，而是补了运行时状态快照、快照浏览和快照回放链路。  
运行中的状态条目可以导出成带 schema 和载荷描述的快照，回放时再根据恢复模式、依赖关系和优先级选择对应的重建逻辑，把目标状态重新导回运行时状态域。

这意味着 `SceneBlueprint` 并不只是“能把蓝图跑起来”，而是具备把运行期状态捕获、解释、回放和定位的能力。对于复杂场景流程、事件链路和条件触发问题，这类能力会显著提升调试效率，也让系统更适合持续演进。

## 结论

`SceneBlueprint` 最适合被定义为一个完整的 Unity 场景级蓝图框架项目。

它真正有价值的地方，不是单独某一个窗口、某一个运行时节点或某一个辅助工具，而是把：

- 定义来源
- 编辑制作
- 场景语义绑定
- 导出契约
- 运行时解释执行
- 状态调试与知识辅助

组织成了同一套系统边界之内的完整闭环。

如果后续进入简历或作品集，最推荐的写法不是拆成多个小项目，而是把 `SceneBlueprint` 当作一个代表“端到端工具框架与运行时设计能力”的重量级项目来呈现。
