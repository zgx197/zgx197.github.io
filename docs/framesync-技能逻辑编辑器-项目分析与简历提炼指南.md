## 一句话定位

这套系统更适合被定义为一套面向确定性 ECS 帧同步技能系统的可视化编辑与预览平台，而不只是一个 Timeline 技能编辑器。

它的核心价值不在于“能拖时间轴”，而在于：

- 把技能逻辑配置、表现时间轴、预览场景、确定性沙盒和最终导出收口串成一条闭环。
- 让技能编辑不再停留在静态配表，而是能够在贴近运行时的环境中验证行为。
- 让旧配置、旧资源、旧轨道逐步进入统一的新编辑链路。

## 项目目标与解决的问题

从当前代码看，这套工具解决的不是“策划能否改技能参数”这种单点问题，而是一组典型的技能工具链问题。

### 1. 技能配置难以可视化编辑的问题

传统技能配置往往以静态表或脚本化数据为主，虽然能表达逻辑，但对复杂技能时序、能力触发顺序、表现层动作和碰撞体配置并不直观。

这套系统通过：

- 蓝图配置资产
- 时间轴轨道和标记
- 统一参数编辑器
- 预览形状编辑

把“技能什么时候做什么”变成了更容易理解和维护的可视化编排流程。

### 2. 技能逻辑与表现时间分离的问题

技能系统里最常见的困难之一，就是逻辑层和表现层时间很容易脱节：

- 逻辑事件按帧执行
- 动画、特效、音效按表现时间播放
- 技能时长和动作时长并不总是天然一致

这套系统通过逻辑轨道、表现轨道、阶段轨道以及统一时间提取机制，把这些内容放在同一编辑入口中管理，降低了配置漂移和多人协作时的理解成本。

### 3. 技能编辑结果与确定性运行时脱节的问题

很多技能工具的问题在于“看起来能编辑”，但真正进入帧同步运行时后，仍然需要重新走配表、重新验证、重新对齐。

这套系统直接连接确定性沙盒和运行时技能资产：

- 数据源直接读取帧同步静态资产
- 预览可直接启动确定性沙盒
- 导出会回写技能配置资产并收口到统一收集器

这让技能编辑器不再只是辅助展示工具，而是真正接到运行时主链路上的生产工具。

### 4. 技能预览和验证成本高的问题

如果技能修改后只能进游戏场景验证，就会遇到：

- 验证链路长
- 复现成本高
- 多个系统干扰调试
- 难以逐帧观察结果

这套系统通过临时预览场景、角色预览、技能挂点、确定性时间服务、沙盒步进和回退机制，把技能验证搬进了编辑器内部，显著缩短了调整和验证的往返成本。

### 5. 资产管理和导出收口分散的问题

技能配置一旦进入多人协作环境，就会遇到：

- 资产散落
- 命名不统一
- 导出目标不一致
- 新旧配置混杂
- 收集器维护依赖手工更新

这套系统补了蓝图资产数据库、自动打标签、增量监听、自动导出到技能收集器等能力，使技能资产的管理、索引和最终收口更加工程化。

## 项目架构分层

从当前代码结构来看，这套技能逻辑编辑器大致可以拆成以下几层：

### 1. 蓝图数据层

这一层负责回答“一个技能在编辑器里如何被抽象和持久化”。

核心职责：

- 保存技能基础信息
- 保存总帧数和阶段信息
- 保存能力调度信息
- 关联时间轴和导出后的技能资产
- 挂接预览配置

核心意义：

- 让蓝图成为独立的技能编辑事实源。
- 让时间轴不再是唯一真相，而是和蓝图数据互相同步。

### 2. 窗口与工作台层

这一层负责回答“用户进入编辑器后，如何切换页面、管理蓝图、查看时间轴、编辑预览和设置”。

核心职责：

- 统一窗口入口
- 页面切换
- 分区绘制
- 共享上下文管理
- 将界面展示和业务逻辑拆分

核心意义：

- 降低编辑器窗口继续膨胀的风险。
- 让后续迁移 UI 方案或新增分区时更容易演进。

### 3. 编辑流程与状态治理层

这一层负责回答“从选择蓝图到进入编辑，再到退出编辑的整段工作流如何保持一致”。

核心职责：

- 创建蓝图与加载蓝图
- 进入 / 退出编辑模式
- 打开 / 关闭预览场景
- Timeline 窗口锁定与解锁
- 角色配置恢复与回写
- 蓝图 ID 冲突检测与上下文状态同步

核心意义：

- 让技能编辑流程从零散按钮操作变成可治理的工作台生命周期。
- 减少切换资源、切换场景、切换预览状态时的错乱和遗留状态问题。

### 4. 时间轴编排层

这一层负责回答“不同技能能力如何映射成时间轴轨道、如何按规则创建和提取”。

核心职责：

- 轨道注册
- 轨道元数据描述
- 轨道工厂
- 分组与分类管理
- 时间轴数据提取
- 损坏轨道检查与清理

核心意义：

- 新能力接入从手工硬编码变成声明式接入。
- 时间轴结构从散乱资产变成可验证、可迁移、可修复的系统。

### 5. 参数编辑与配置映射层

这一层负责回答“能力参数如何在编辑器里被稳定编辑，并映射回运行时配置”。

核心职责：

- 通用参数绘制
- 枚举显示名统一
- 开始帧和能力 ID 自动维护
- 配置引用与表格配置还原
- 碰撞形状编辑和预览形状管理

核心意义：

- 降低技能参数编辑的门槛。
- 减少人工同步 `StartFrame / AbilityId / Duration` 这类机械劳动和错误风险。

### 6. 预览场景与可视化层

这一层负责回答“技能编辑结果如何在编辑器中被可视化验证”。

核心职责：

- 临时预览场景创建与恢复
- 角色模型加载与动画绑定
- 技能挂点编辑
- 碰撞体和预览形状绘制
- 场景基础设施锁定
- 外部动作时间轴挂接与播放

核心意义：

- 让预览从“静态看配置”升级为“动态看技能行为”。
- 为策划和程序提供更短的验证回路。

### 7. 权威时间与确定性验证层

这一层负责回答“如何统一驱动 Timeline 时间、预览状态和确定性验证流程”。

核心职责：

- 时间变化监听
- 时间跳变检测
- 播放状态同步
- 多消费者按优先级更新
- 沙盒生命周期管理
- 实体创建与销毁
- 沙盒角色创建
- 技能释放
- 播放、暂停、步进、回退、快照
- 动画状态机更新

核心意义：

- 让编辑器内部不只有一个时间读数，而是有统一的时间驱动中心。
- 让技能验证不只依赖美术表现，而是直接落到确定性运行逻辑中。
- 让技能调试更接近真实运行时。

### 8. 数据源适配与旧系统接线层

这一层负责回答“编辑器如何从旧静态数据、旧 Timeline 和既有技能资源中拿到可用信息”。

核心职责：

- 数据源 Provider 抽象
- 多 Provider 注册与切换
- TimelineId 查询与技能名反查
- 技能资源自动加载
- 旧数据自动重载
- 机关相关时间数据查询

核心意义：

- 让编辑器不需要写死在某一份静态资源或某一种数据格式上。
- 让旧系统接入和后续扩展拥有统一边界，而不是继续在业务代码里硬绑资源路径。

### 9. 导入导出与资产数据库层

这一层负责回答“编辑器资产如何导入、导出、索引、监听和收口”。

核心职责：

- 从已有技能配置反向生成蓝图和时间轴
- 从当前蓝图导出运行时技能配置
- 蓝图资产打标签
- 资产数据库索引
- 监听资产变化做增量更新
- 自动导出到技能收集器

核心意义：

- 把技能编辑工具真正接到团队资产工作流里。
- 降低旧资产迁移、新资产收口和多人协作时的混乱度。

## 最有代表性的亮点

下面这些亮点，是后续最适合写进简历和作品集的内容。

### 亮点 1：把技能编辑做成了“蓝图 + 时间轴 + 导出”的双层结构

这套系统并不是直接让时间轴承担全部职责，而是明确区分了：

- 蓝图配置资产
- 时间轴可视化编排
- 最终运行时技能配置

这让技能编辑、时间轴表现和最终导出资产之间形成了更清晰的边界。

这个点适合在简历里表达为：

- “设计技能蓝图与时间轴双层结构，解耦编辑态配置、可视化编排与运行时导出数据”

### 亮点 2：时间轴轨道体系做成了可扩展平台，而不是硬编码面板

当前轨道体系已经具备：

- 轨道自动注册
- 按类别分组
- 按能力类型映射到轨道
- 轨道自动补齐
- 缺失轨道修复

这说明它的重点不是“做几个轨道”，而是搭建一套可扩展的技能编排框架。

这个点适合在简历里表达为：

- “设计元数据驱动的技能时间轴轨道体系，支持轨道自动注册、分组管理与缺失修复”

### 亮点 3：把逻辑层能力、表现层能力和阶段控制放进同一编排入口

技能工具常见的问题是逻辑层和表现层分属不同文件、不同时间体系，导致改动难以联动。

这套系统将：

- 技能逻辑事件
- 表现层动作和特效
- 技能阶段信息
- 机关相关能力

统一纳入同一个时间轴编排入口中管理，大幅提升了技能结构的可读性和协作效率。

这个点适合在简历里表达为：

- “统一技能逻辑、表现与阶段信息的可视化编排流程，降低技能时序配置的理解和维护成本”

### 亮点 4：确定性沙盒直接接入技能编辑器

这可能是整套系统里最有辨识度的地方之一。

你做的不是普通预览播放，而是把编辑器直接接到确定性沙盒中，支持：

- 播放 / 暂停
- 变速
- 逐帧步进
- 回退
- 快照恢复
- 沙盒角色创建和技能释放

这意味着技能验证可以尽量贴近真实的帧同步运行环境。

这个点适合在简历里表达为：

- “将确定性 ECS 帧同步沙盒接入技能编辑器，支持逐帧步进、回退与快照验证，提升技能调试效率”

### 亮点 5：预览场景不是简单播放，而是完整的编辑验证环境

预览系统已经具备：

- 临时场景创建与恢复
- 角色模型和动画挂接
- 技能挂点可编辑
- 预览形状绘制
- 场景基础设施锁定
- 外部动作时间轴接入

它更像一个专门为技能验证准备的小型工作台，而不是单纯的播放窗口。

这个点适合在简历里表达为：

- “构建技能预览工作台，支持角色预览、技能挂点编辑、碰撞范围可视化与动作时间轴联动验证”

### 亮点 6：把运行时技能配置和编辑器资产做成双向转换

当前系统不仅能导出，还支持从已有技能配置反建蓝图和时间轴。

这说明你解决的是“旧资产如何进入新工具链”的问题，而不是只支持从零新建。

这个点适合在简历里表达为：

- “实现技能配置资产与蓝图编辑资产的双向转换，支撑旧技能数据迁移和新工具链接入”

### 亮点 7：资产数据库与自动导出收口

这部分非常能体现工程化思维。

你已经做了：

- 资产标签管理
- 资产数据库索引
- 增量监听
- 自动校验
- 自动导出到技能收集器

这意味着技能编辑器的产出不是停在本地文件，而是能够稳定进入团队资源收口流程。

这个点适合在简历里表达为：

- “构建技能资产数据库与自动导出链路，实现蓝图资产索引、增量更新与统一收口”

### 亮点 8：兼容旧轨道、旧时序和旧资源的演进治理

代码里能明显看出这套系统不是从零空白世界里长出来的，而是在持续吸收旧数据和旧工作流：

- 前后摇轨道废弃后保留兼容字段
- 老 Timeline 自动补分组和轨道
- 支持旧配置命名回退
- 支持覆盖重建和重新导入

这类“系统演进治理”非常重要，也很适合在简历里体现工具架构能力。

这个点适合在简历里表达为：

- “推动技能编辑工具向新架构迁移，补齐旧轨道兼容、资产修复和旧数据导入能力”

### 亮点 9：把编辑器做成了可治理的工作台生命周期

这套系统不是“点开窗口就开始改配置”的简单模式，而是围绕完整编辑流程建立了清晰的状态切换链路：

- 进入编辑模式时自动打开预览场景
- 自动初始化沙盒与 Timeline 编辑器
- 自动恢复预览角色配置
- 退出编辑模式时自动回写配置并清理现场

这说明你在做的不是单个功能，而是一套面向日常使用的编辑工作台。

这个点适合在简历里表达为：

- “梳理技能编辑工作台生命周期，统一管理蓝图切换、预览场景、Timeline 锁定、沙盒初始化与配置回写流程”

### 亮点 10：建立统一的权威时间驱动机制

这套编辑器并不是简单读取 Timeline 当前时间，而是额外抽了一层统一时间服务，用来管理：

- 当前播放状态
- 时间跳变检测
- 多个预览模块的同步更新
- 时间消费者的优先级调度

这让碰撞预览、角色预览、沙盒验证等能力都能围绕同一套时间上下文运转。

这个点适合在简历里表达为：

- “设计统一时间驱动机制，协调 Timeline、预览模块与沙盒验证的时序同步，提升编辑与调试稳定性”

### 亮点 11：数据源接入做成了可替换的 Provider 层

从代码看，编辑器没有把外部技能数据写死在某个文件路径和某份静态资源上，而是做了明确的数据源抽象：

- 支持多个 Provider 注册
- 支持运行时接入 Provider
- 支持缓存失效和自动重载
- 支持通过 TimelineId 反查技能资源

这个设计很适合体现你在旧系统接线和后续扩展上的架构意识。

这个点适合在简历里表达为：

- “抽象技能数据源 Provider 层，统一承接旧静态数据查询、资源反查与编辑器接线逻辑，降低工具对底层数据结构的耦合”

### 亮点 12：信号系统具备半自动建模能力

信号相关能力并不是让用户手工记忆和填写全部配置，而是通过扫描、筛选和推荐机制降低配置成本：

- 自动扫描可用信号
- 白名单控制可见范围
- 按参数类型推荐来源
- 配合可搜索选择面板做快速配置

这个点能很好体现你不是只关注“功能能不能做出来”，而是也在关注“工具好不好用”。

这个点适合在简历里表达为：

- “构建信号能力的半自动配置机制，支持信号扫描、参数来源推荐与搜索式选择，降低复杂技能配置门槛”

### 亮点 13：工具自身具备可持续演进的架构

这一点在代码和设计文档里都比较明显。你不是把所有逻辑堆在一个 EditorWindow 里，而是逐步沉淀出：

下面这部分按当前简历网站更常用的结构整理，尽量对齐你之前 `StageDesigner` 那份文档的用法，后续可以直接复制再按篇幅微调。

### 项目介绍

这是一套面向确定性 ECS 帧同步技能系统的可视化编辑平台，目标不是只做一个技能时间轴面板，而是统一承接技能配置、时间编排、预览验证和导出收口流程。项目围绕技能蓝图、时间轴轨道、预览场景、确定性沙盒和资产数据库逐步构建出完整闭环，使技能编辑从传统的静态配表方式升级为更直观、更可验证、也更容易接入团队工作流的工具体系。

### 主要工作

#### 整体设计

1. 技能蓝图与时间轴双层结构设计：我将技能编辑拆成“蓝图配置资产”和“时间轴可视化编排”两层，使技能基础信息、总帧数、预览配置和能力调度可以稳定沉淀在蓝图资产中，而具体的时序表达和逻辑组织则通过时间轴完成。这样既保留了可视化编辑的优势，也避免把所有数据都绑定在单一时间轴资源上。

2. 技能逻辑、表现和阶段信息统一编排：围绕技能编辑流程，我推动把逻辑层能力、表现层能力、技能阶段和部分机关行为统一纳入同一个时间编排体系中，让不同类型的技能行为可以在同一个工作台中观察、调整和导出，降低了逻辑和表现脱节的风险。

3. 编辑工作台生命周期治理：我围绕蓝图选择、进入编辑、预览场景初始化、Timeline 窗口锁定、角色恢复和退出编辑回写这条链路，梳理了完整的工作台流程。这样技能编辑不再依赖操作者记住一堆顺序步骤，而是进入、编辑、退出都有明确且稳定的系统行为。

4. 编辑器与确定性运行时打通：我没有把这套工具做成一个只看动画效果的编辑器，而是直接接入确定性沙盒，使技能编辑结果能够在接近真实帧同步运行环境的条件下验证。这样在技能调整时，既能看表现，也能看逻辑执行、技能释放和逐帧状态变化。

5. 权威时间与多模块同步设计：为了让 Timeline、碰撞预览、角色预览和沙盒回放保持一致，我补了统一的时间驱动机制，负责处理播放状态、时间跳变和多模块更新顺序。这样不同预览能力不需要各自维护一套时间判断逻辑，整体调试体验也更稳定。

6. 资产管理与导出收口工程化：我围绕技能资产建立了导入、导出、索引、监听和自动收口流程，让蓝图编辑器产出的结果不只是停在本地资源，而是能稳定进入团队的技能配置收集链路，减少人工同步和遗漏问题。

#### 重点模块

1. 可扩展技能轨道体系：我设计了统一的技能轨道描述和注册机制，使新能力接入不需要在多个窗口和工具类中重复改逻辑，而是可以通过轨道声明进入创建、提取、导入和导出流程。这让时间轴不再只是手工堆轨道，而是具备平台化扩展能力。

2. 技能参数编辑与自动维护：我为技能参数编辑补齐了统一绘制、显示名称映射、开始帧自动同步、能力编号唯一性维护和碰撞体形状编辑等能力，减少了策划和程序在参数维护中的重复劳动，也降低了人工填写带来的错误风险。

3. 预览场景与技能挂点编辑：我构建了独立的技能预览场景，支持角色预览、技能挂点调整、碰撞范围可视化和场景基础设施锁定。这样做的目的不是单纯让预览更好看，而是让技能验证过程更聚焦、更安全，避免无关对象干扰操作。

4. 确定性沙盒验证链路：我把技能编辑器与确定性沙盒打通，支持播放、暂停、逐帧步进、回退、快照和沙盒角色技能释放测试，使技能验证从“进游戏手动复现”转为“在编辑器中直接验证”，显著缩短了调试和迭代的往返成本。

5. 数据源接入与旧系统联动：我把旧静态数据查询、TimelineId 反查、技能资源加载等能力收拢成可替换的数据源接入层，使编辑器不需要直接耦合某一份底层资源结构，也为后续接入更多技能数据来源预留了扩展空间。

6. 信号系统半自动配置：围绕复杂技能中的信号触发需求，我补了信号扫描、白名单过滤、参数来源推荐和搜索式选择能力，减少了手工配置时对底层枚举和参数结构的记忆负担，也降低了误配概率。

7. 技能配置双向转换：我实现了从现有技能配置资产反向生成蓝图和时间轴的导入能力，也实现了从当前蓝图和时间轴提取数据并回写运行时技能配置的导出能力。这使新工具可以兼容旧资产，同时也为后续全面迁移到新编辑流程提供了基础。

8. 蓝图资产数据库与自动收口：我构建了蓝图资产数据库、自动标签、增量监听和自动导出到技能收集器的流程，让技能资产可以被统一索引、自动校验并稳定进入最终收口环节，提升了多人协作环境下的资产管理效率。

9. 旧系统兼容与演进治理：在工具迭代过程中，我补了旧轨道兼容、旧资源回退、时间轴分组迁移、损坏轨道检查与清理等能力，使新编辑器不是只能服务新资源，而是能够逐步吸收历史资产，降低工具升级阻力。

10. 工具自身分层与可维护性治理：在功能不断增加的过程中，我没有继续把逻辑堆在单个窗口脚本里，而是逐步拆出了上下文、绑定层和业务服务层，统一处理 Undo、状态通知和冲突校验。这让编辑器后续加功能时不必持续放大技术债，也更适合长期演进。
