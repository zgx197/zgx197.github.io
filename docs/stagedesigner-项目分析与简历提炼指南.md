# StageDesigner 项目分析与简历提炼指南

## 文档目的

这份文档不是对外展示稿，而是后续生成简历内容、项目详情页内容、作品集介绍文案的内部依据。

目标有三点：

- 先把 `StageDesigner` 的真实项目定位说清楚。
- 再把最值得写进简历的亮点提炼出来。
- 最后明确哪些内容适合写、哪些内容不宜过度表述。

需要特别说明：

- 本文基于对 `StageDesigner` 与其相关 `DungeonArchitect` 集成代码的多轮阅读分析整理而成。
- 当前判断前提是：`StageDesigner` 约 95% 代码由本人完成。
- `DungeonArchitect` 是被整合和改造的底层系统，不应表述为“本人从零开发了 DungeonArchitect”。

---

## 一句话定位

`StageDesigner` 更适合被定义为一套面向多场景类型的 Unity 场景设计平台，而不只是一个单点的关卡编辑器。

它的核心价值不在于“能编辑地图”，而在于：

- 用统一入口承接多类场景编辑流程。
- 用统一会话模型管理编辑生命周期。
- 用模式系统和交互状态机治理编辑行为。
- 用 capability、路径策略、导出与同步协议承接生产流水线。

## 推荐项目命名

如果后续要进入简历或作品集，推荐使用以下命名方式之一：

- `StageDesigner：Unity 通用场景设计平台`
- `StageDesigner：模块化场景编辑与导出工具链`
- `StageDesigner：面向多场景类型的 Unity 场景设计框架`

不建议只写成：

- `关卡编辑器`
- `地图编辑器`

原因是这会把项目价值压扁，无法体现统一会话、模式治理、导出同步、配置分层、兼容演进这些平台能力。

## 项目目标与解决的问题

从代码和文档来看，`StageDesigner` 解决的不是单一功能问题，而是一组长期演进中的编辑器问题：

### 1. 统一入口问题

历史上不同场景类型可能各有各的入口、各有各的启动参数、各有各的布局和恢复逻辑。

`StageDesigner` 通过：

- `SceneIdentity`
- `SceneProfile`
- `SceneSessionRequest`
- `EditorSession.StartSession(request)`

把这些分叉入口逐步收敛成统一会话主链路。

### 2. 多场景类型扩展问题

项目不再只服务传统数字关卡，还在向以下方向扩展：

- `Level`
- `Hub`
- `HomeMap`
- `BattleTest`
- 后续的 `PuzzleTest / PerformanceTest / SkillTest / ArtTest`

这要求编辑器不能继续依赖“关卡号就是唯一身份”的旧模型，而必须显式建模：

- 场景类型
- 稳定场景标识
- 能力集合
- 模块装配方式
- 资产命名与导出路径

### 3. 编辑行为复杂度问题

当工具越来越多、模式越来越多、交互越来越复杂时，如果仍靠按钮状态和散落脚本来驱动，系统会很快失控。

`StageDesigner` 通过：

- `ModeRegistry`
- `ModeManager`
- `ModeMiddleware`
- `InteractionManager`
- 选择状态机

把“模式切换、互斥、依赖、锁定、触发器、交互状态”做成了可治理的系统。

### 4. 生产流水线接入问题

编辑器不是停在“能画图”就结束，它还要承接：

- 运行时数据导出
- 帧同步地图导出
- 蓝图运行时数据导出
- 导航描述导出
- 游戏工程同步
- 路径命名和目录规范统一

`StageDesigner` 在这方面已经形成了导出 / 同步 / 路由 / 配置 / 校验的一体化链路。

### 5. 外部内容回流与协作问题

真实项目里，场景内容并不只来自编辑器内手工搭建，还会来自：

- 基于 `Cell` 的区域白模与走廊数据
- 美术制作的大模块 `Prefab`
- 历史白模 `Prefab`
- 外部工具导出的 `JSON` 坐标
- TA 工具链生成的 `TerrainBaker / TerrainBuild` 运行时产物

这要求编辑器不仅要“能编辑”，还要能把外部内容稳定回流进统一数据模型，并把编辑结果再送回生产流水线。

从当前代码来看，`StageDesigner` 已经在做这件事，而且不是一次性脚本，而是逐步沉淀成窗口、导入策略、坐标规约、去重覆盖、导出服务、同步服务的一整套能力。

## 项目架构分层

从当前代码结构来看，`StageDesigner` 可以拆成以下几层：

### 1. 统一场景描述层

这一层负责回答“当前编辑的到底是什么场景”。

关键对象：

- `SceneIdentity`
- `SceneProfile`
- `SceneSessionRequest`
- `SceneModuleContext`

核心意义：

- 不再依赖场景名正则或旧 `levelId` 字段做唯一事实源。
- 让场景类型、显示名、稳定标识、能力声明、路径策略显式可读。

### 2. 会话与模块装配层

这一层负责回答“这个场景启动编辑器时，需要初始化哪些系统”。

关键对象：

- `EditorSession`
- `SceneModuleSetRegistry`
- `EnvironmentModule`
- `MapEditorModule`
- `DungeonArchitectModule`
- `InteractionModule`
- `HomeMapModule`

核心意义：

- 把编辑器初始化顺序和依赖关系收敛到模块协议。
- 让不同场景类型共享统一宿主，同时又保留必要差异。

### 3. Redux 状态管理层

这一层负责回答“当前编辑器状态由谁统一管理、如何变更、如何追踪”。

关键对象：

- `Store`
- `StoreProvider`
- `RootReducer`
- `EffectMiddleware`
- `ModeMiddleware`

核心意义：

- 避免状态散落在 EditorWindow、SceneGUI、MonoBehaviour 中。
- 明确区分状态更新与副作用处理。
- 为调试窗口、Action 历史、测试回归提供稳定基础。

### 4. 模式系统与交互状态机层

这一层负责回答“当前允许做什么、不能做什么、进入和退出工具模式时要发生什么”。

关键对象：

- `ModeDefinitionsAsset`
- `ModeRegistry`
- `ModeManager`
- `TransitionContext`
- `InteractionManager`
- `BatchSelectionHandler`
- `IdleState / RectSelectingState / SelectedState`

核心意义：

- 让模式关系从隐式代码约定，升级为可视化、可验证、可维护的规则系统。
- 让编辑交互从散乱事件处理升级为状态机。

### 5. 底层系统适配层

这一层负责回答“如何与外部或历史系统协作，但不让它们污染新的主链路”。

关键对象：

- `DungeonArchitectAdapter`
- `MapEditorAdapter`
- `ArtSceneAdapter`
- `DungeonArchitectInteractablesEditor` 兼容层

核心意义：

- 复用既有底层能力。
- 控制边界，避免旧系统直接侵入 Redux / Session 主链路。

### 6. 资产路由与导出同步层

这一层负责回答“导出什么、导到哪里、同步到哪里、不同场景类型如何复用同一套规则”。

关键对象：

- `SceneAssetPathRouter`
- `SceneArtifactDefinition`
- `SceneArtifactPathResolver`
- `SceneFilePathResolver`
- `PathTemplateResolver`
- `ExportContext / SyncContext`
- `ExportStep / SyncStep`
- `ExportPipeline / SyncPipeline`

核心意义：

- 把导出与同步从“服务类里拼路径”提升为声明式协议。
- 把步骤适用性从 UI 硬编码提升为 step 元数据 + capability 过滤。

### 7. 外部内容导入与可视化辅助层

这一层负责回答“如何把外部数据、白模、大模块、美术场景和地形工具链接进统一编辑体验”。

关键对象：

- `CorridorImportWindow`
- `PrefabCorridorImporter`
- `JsonCorridorImporter`
- `DaMoKuaiNodeCollector`
- `ImporterUtils`
- `CellAreaVisualizer`
- `ArtSceneAdapter`
- `HomeMapTerrainExportService`

核心意义：

- 让 `Cell`、Prefab、JSON、美术模板场景、TA 导出工具链不再是散落脚本，而是进入统一工具体系。
- 让编辑器具备“内容回流”和“生产接线”能力，而不只是本地可视化编辑能力。

## 最有代表性的亮点

下面这些亮点，是后续最适合进入简历和作品集的内容。

### 亮点 1：统一场景身份模型

项目不再把“数字关卡号”当成唯一主键，而是显式抽象出：

- `SceneType`
- `SceneCode`
- `SceneName`
- `DisplayName`
- `SceneProfile`

这让 `Level / Hub / HomeMap / BattleTest` 这类场景能进入同一条主链路。

这是平台化改造的起点，也是整个项目最核心的抽象之一。

### 亮点 2：统一会话入口与模块装配

`EditorSession.StartSession(request)` 成为真实主入口，旧入口被收缩到兼容层。

这意味着：

- 启动逻辑统一
- 参数模型统一
- 模块初始化顺序统一
- 多场景类型接入成本降低

这个点很适合简历里表达为：

- “主导统一编辑会话模型与模块装配机制”
- “将多类场景编辑流程收敛到同一会话入口”

### 亮点 3：模式系统 + 关系矩阵

这部分是 `StageDesigner` 非常有辨识度的亮点。

项目不仅有模式系统，而且把模式之间的：

- 互斥
- 依赖
- 锁定
- 双向锁定
- 同组互斥

做成了关系矩阵和配置资产。

这说明工具间关系不是散落在代码条件判断里，而是被收敛成一套可视化规则系统。

这个点很适合简历里表达为：

- “设计并实现编辑器模式治理系统，支持模式依赖、互斥、锁定与关系矩阵可视化维护”

### 亮点 4：交互状态机与复杂编辑体验治理

选择、框选、点选、拖拽移动、冲突预览、快捷键操作，这些行为没有混在一个 SceneGUI 函数里，而是拆成：

- `InteractionManager`
- Handler
- Selection 状态机
- Adapter 执行层

这说明你在意的不只是“功能能用”，而是“复杂交互如何长期可维护”。

### 亮点 5：导出 / 同步流程平台化

项目已经不是“几个导出按钮”，而是有：

- 上下文对象
- 步骤元数据
- capability 适用性
- 步骤依赖
- 自动补齐系统步骤
- 统一执行计划
- DataManager UI 展示与原因反馈

这个点很适合简历里表达为：

- “重构场景数据导出与同步流程，建立基于 capability 和步骤元数据的执行编排体系”

### 亮点 6：命名策略与资产路由统一

当前已经形成了多种命名策略与统一路由入口：

- `LegacyNumeric`
- `SceneCode`
- `NamedScene fallback`

并逐步把导出路径、运行时路径、游戏侧同步路径统一到路由层。

这是非常典型的平台能力，适合在项目详细说明里重点写。

### 亮点 7：项目设置与个人设置分层

这部分是团队协作型工具的重要特征。

`StageDesignerSettings` 负责：

- 项目级共享配置
- 进入版本控制
- 团队统一事实源

`StageDesignerPrefs` 负责：

- 个人路径偏好
- 工具本地设置
- 流程步骤开关
- 不进入版本控制

这个点很适合体现你对团队协作和工具产品化的理解。

### 亮点 8：恢复、预检查、调试与测试能力

`StageDesigner` 不仅有主功能，还有：

- 启动前检查
- 会话恢复
- 调试窗口
- Action 历史
- 路由与步骤元数据测试

这说明项目是按“长期维护平台”而不是“短期脚本工具”来建设的。

### 亮点 9：支持基于 Cell 的场景构建与区域可视化

这部分能力说明 `StageDesigner` 已经不只是“摆物件式编辑器”，而是在承接更底层的格子化场景组织方式。

从代码看，至少有两类明确信号：

- `DungeonArchitectModule` 在初始化阶段会调用 `BuildCellsWithData()`，自动导入场景数据并重建模型。
- `CellAreaVisualizer` 会读取区域多边形，做 `PointInPolygon` 过滤，显示多边形轮廓、AABB、生成后的 `Cell` 网格，并暴露导出相关选项。

这意味着你做的不是简单的格子显示，而是把：

- 区域定义
- Polygon 到 Cell 的转换
- 可视化校验
- 导出策略验证

串成了一条可操作的工作流。

这个点适合在简历里表达为：

- “支持基于 Cell 的场景区域构建与可视化校验，承接白模/寻路相关基础编辑流程”
- “实现区域多边形到 Cell 网格的转换与可视化工具，降低地编数据校验成本”

### 亮点 10：支持大模块、旧白模与 JSON 坐标的多源导入

这一块非常能体现“工具接生产”的价值。

当前导入窗口已经不是单一入口，而是把外部走廊数据拆成三类来源：

- 大模块 `Prefab`
- 旧白模 `Prefab`
- 外部 `JSON` 坐标

其中大模块导入并不是依赖死板层级，而是：

- 递归扫描 `DaMoKuai_BaiHe` 入口节点
- 支持未激活节点
- 收集叶子节点
- 按统一网格规则做世界坐标到 `Cell` 坐标转换
- 对同坐标、同 `XZ` 不同 `Y` 的情况做去重与覆盖决策
- 导入后自动重建场景模型

这说明你解决的并不是“导入一个 prefab”这么浅的一层，而是把外部内容回流到统一场景数据结构里。

这个点适合在简历里表达为：

- “实现大模块 Prefab、旧白模 Prefab 与 JSON 坐标的多源导入链路，打通外部内容向关卡编辑数据的回流流程”
- “设计坐标规约、重复位置去重与重建机制，提升外部场景数据导入的稳定性”

### 亮点 11：打通美术模板场景与 TA TerrainBaker 工具链

这一块是非常有代表性的“生产流水线接入能力”。

从 `ArtSceneAdapter`、`ArtSceneEffectHandler`、`ArtSceneConfig`、`HomeMapTerrainExportService` 可以看出，当前系统已经形成一条比较完整的链路：

- 使用固定美术模板场景做预览，而不是每个关卡各自维护一套独立美术场景
- 把当前场景导出的 `SceneModel prefab` 挂载到固定挂载点
- 自动隐藏地编场景、切换预览模式、处理已有预制体冲突
- 通过反射查找并更新 `TerrainBaker` 包围盒参数
- 通过 `EditorApplication.ExecuteMenuItem("GameObject/TerrainTools/Export")` 调用既有 TA 工具，而不是侵入式改底层
- 导出后重命名目录、修正运行时路径、同步到游戏侧目录

`HomeMapTerrainExportService` 这条线更进一步，已经做到：

- 导出前临时把 `HomeMapRoot` 注入 `TerrainBaker.staticLayers`
- 临时剥离编辑器专用组件，避免游戏侧出现 `Missing Script`
- 导出后通过 `Undo` 自动恢复
- 同步 Terrain 产物到游戏工程
- 处理导出后场景对象状态恢复

这类能力非常适合突出“我把工具真正接到了项目生产链路里”，而不只是“我做了个编辑器界面”。

这个点适合在简历里表达为：

- “打通美术模板场景、SceneModel 挂载与 TerrainBaker/TerrainBuild 导出链路，提升关卡内容到运行时资源的交付效率”
- “以非侵入方式接入 TA 地形工具链，补齐参数更新、导出、同步、恢复与兼容处理流程”

## 对 `DungeonArchitect` 的正确表述边界

后续写简历或项目介绍时，要把这部分说准确。

### 可以这样写

- 基于 `DungeonArchitect` 等底层能力，设计并实现上层统一场景设计平台
- 封装底层地形编辑与构建系统，建立适配层、会话层与交互层
- 将原有编辑器链路整合进统一会话与导出框架

### 不建议这样写

- 独立从零开发 `DungeonArchitect`
- 独立开发整个底层地形生成引擎
- 完全自主实现全部地图构建底层

原因是这会把“整合与平台化改造”误写成“重写底层插件”，不够准确。

## 最适合写进简历的能力画像

如果从招聘视角看，`StageDesigner` 最能体现的不是某个单一功能，而是以下几类能力：

### 1. 工具架构能力

- 会做统一入口
- 会做会话模型
- 会做模块装配
- 会做状态管理
- 会做兼容层治理

### 2. 编辑器交互设计能力

- 会设计模式系统
- 会设计工具间关系约束
- 会做 SceneView 交互状态机
- 会做复杂编辑行为的可维护组织

### 3. 工程化能力

- 会做导出 / 同步流水线
- 会做能力声明与执行计划编排
- 会做路径与命名策略统一
- 会做项目配置与个人偏好分层
- 会做外部内容导入与生产链路接入

### 4. 平台化演进能力

- 不只做当前需求
- 会为后续场景类型扩展预留结构
- 会管理历史兼容层
- 会通过文档、测试、调试工具降低演进风险

## 可直接用于简历网站的成稿

下面这部分按你当前简历网站里更常用的结构整理，尽量贴近你之前 `2D俯视角沙盒修仙模拟类游戏` 的组织方式，后续可以直接复制后再按页面篇幅微调。

### 项目介绍

`StageDesigner` 是我主导开发的一套 Unity 通用场景设计平台，目标不是单点解决某一个关卡工具问题，而是统一承接多种场景类型的编辑、预览、导出与同步流程。项目在保留既有底层能力的基础上，逐步建立了统一的场景标识体系、统一入口、模式系统、交互状态机、资源路径管理与生产流水线接入机制，使编辑器从早期偏单点的地图工具演进为可持续扩展的场景设计平台。

### 主要工作

#### 整体设计

1. 统一场景身份与主流程入口：我将编辑器从依赖旧关卡编号和分散入口的模式，逐步收敛到统一的场景标识、场景配置和启动请求体系中，让普通关卡、首页地图、测试场景等不同场景类型都能在同一套启动、装配和导出框架下运行，显著降低了后续新场景类型接入成本。

2. 模块化编辑器装配体系：围绕统一会话模型，我设计了模块装配机制，将环境初始化、地图编辑、底层构建系统、交互系统、首页地图能力等拆分为可组合模块，并通过统一的模块上下文和优先级机制组织初始化顺序，避免历史上“入口不同导致依赖关系失控”的问题。

3. 模式系统与交互治理框架：针对编辑器中不断增加的工具和操作形态，我设计了模式系统、关系矩阵与交互状态机，将模式之间的依赖、互斥、锁定、双向锁定等关系从隐式代码逻辑提升为可视化、可配置、可验证的规则体系；同时把点选、框选、拖拽、冲突预览等场景编辑操作拆成清晰的状态与处理流程，提升复杂交互的可维护性。

4. 资源路径与导出同步平台化：我没有把导出链路继续做成“不同窗口里各自拼路径”的方式，而是推动建立统一的导出 / 同步体系，把导出条件、步骤顺序、路径解析和执行计划收敛到同一套规则中，统一管理场景资源命名、导出目录、运行时资源路径以及同步到游戏工程的规范，让编辑器真正进入生产流水线。

#### 重点模块

1. 统一场景描述与路径管理：我设计并推进统一的场景描述和路径管理机制，明确区分场景类型、稳定标识、显示名称、能力范围和资源路径规则，逐步替代旧的数字关卡命名模型，使不同场景不再依赖临时约定，而是进入统一的标准化描述体系。

2. 编辑器模式系统与关系矩阵：我实现了模式注册、模式管理、流程协调和关系矩阵维护能力，将编辑器工具之间的互斥、依赖、锁定关系可视化。这样做的价值不只是让切换更安全，更重要的是使后续新增工具时能基于规则接入，而不是在多个窗口和脚本里重复埋判断。

3. 场景编辑交互状态机：我将编辑器中的选择、框选、拖拽移动、冲突检测、批量编辑等行为拆成状态机与分层处理流程，避免所有逻辑都堆在同一个场景交互入口里。这样既提升了交互体验的一致性，也让后续扩展新的编辑工具时能够复用已有交互基础设施。

4. 基于格子的场景构建与区域可视化：我支持了基于格子的场景数据构建流程，并补充了区域可视化工具，用于把多边形区域转换为格子网格、显示包围范围、校验导出策略和观察生成结果。这部分能力承接了场景白模、走廊布局和寻路相关数据的基础工作流，让编辑器具备更强的底层空间组织能力。

5. 外部内容回流与多源导入：为了解决内容不只来自编辑器内部的问题，我实现了多源导入链路，支持导入美术制作的大型场景模块、历史白模资源以及外部坐标数据，并统一完成节点扫描、坐标转换、重复位置去重、同平面不同高度覆盖决策和场景重建。这使外部内容能够稳定回流到编辑器统一的数据模型中，而不是依赖一次性脚本处理。

6. 美术模板场景与地形工具链接入：我设计并实现了美术模板场景预览链路，将当前场景导出的关卡模型挂载到固定模板场景中进行预览，并以非侵入方式接入地形烘焙工具链，支持包围盒更新、运行时地形资源导出、目录重命名、路径修正与同步到游戏工程。这部分工作实质上打通了“编辑器数据 -> 美术预览 -> 运行时资源”的生产交付链路。

7. 项目设置与个人设置分层：我将团队共享配置与个人本地偏好进行了明确拆分，让团队流程配置进入版本管理，而本地路径、调试开关、临时偏好则保留在个人环境里，减少多人协作下的配置污染问题。

8. 稳定性、恢复与调试能力建设：为支撑工具长期演进，我补充了预检查、会话恢复、调试窗口、测试菜单和模式配置校验等能力，提升了编辑器在复杂项目环境下的可恢复性、可观测性和可维护性，而不是把它当成只能靠人工经验维护的临时工具。
